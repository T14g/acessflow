Como o AccessFlow foi montado, em ordem

Texto para quem está começando. Cada passo diz o que entrou no projeto e qual arquivo abrir para ver isso com os próprios olhos.

A ideia em uma frase

Uma pessoa pede acesso a um sistema fictício. A API anota o pedido e deixa um recado numa tabela. Outro programa, o worker, lê esse recado e conclui o acesso num diretório que também é só uma tabela. Nada disso sai do computador. A empresa Helios e as pessoas Ana, Bruno, Clara e Diego são inventadas.

O que já temos

  • Documentação do desenho, em docs/.
  • Banco MySQL accessflow, com tabelas e quatro usuários de demonstração. Senha de todos: Helios-demo-1.
  • API em http://127.0.0.1:3000. A página fica em http://localhost:5173. A raiz da API não é uma tela; o teste de vida é /health.
  • Página simples: entrar, pedir um perfil, ver a nota de risco, aprovar ou recusar, sair.
  • Worker separado, que transforma uma aprovação em concessão simulada.
  • Testes automáticos da API e do conector. O comando é npm test.

Dois commits já existem: a fundação (75cd897) e a API com a página (cd2bf9a). O worker e o ajuste do botão Sair estão no disco e ainda não foram commitados.

Passo a passo do que foi feito

  1. Olhar a máquina antes de escolher ferramenta

    O PDF do plano pedia PostgreSQL. Nesta máquina o banco instalado é o MySQL 8.3, com o HeidiSQL para enxergar as tabelas. A decisão foi usar só esse MySQL. PostgreSQL, Docker e serviços pagos ficaram de fora.

    Abra docs/adr/0002-mysql-only.md.

  2. Escrever o plano antes do código

    Primeiro entrou a pasta, o README e as decisões. Ainda não havia tela nem servidor. O objetivo era um laboratório local de gestão de acessos, com um módulo de risco chamado AccessGuard.

    Abra README.md, docs/architecture.md e a pasta docs/adr/.

  3. Desenhar o contrato, ainda sem ligar o servidor

    Aqui ficaram combinados os papéis, as tabelas, os endereços da API e a lista de eventos. Papéis: colaborador, gestor, administrador e analista de segurança. O analista olha. Quem aprova é o gestor do beneficiário, ou o administrador. Ninguém aprova o próprio pedido.

    Abra docs/contracts.md, docs/data-model.md, docs/api.md e docs/events.md.

  4. Criar o banco vazio e o usuário da aplicação

    No HeidiSQL, com a conta administrativa, foi criado o banco accessflow. O programa não usa essa conta administrativa. Ele entra com o usuário accessflow. No Windows o MySQL viu a conexão como localhost, então esse usuário precisou existir para localhost e para 127.0.0.1. A senha mora só no arquivo .env, que o Git ignora.

    Abra .env.example para ver os nomes das variáveis, sem a senha real. O .env é a cópia local.

  5. Criar as tabelas com a migração

    Migração é um arquivo SQL que cria a estrutura: usuários, sessões, sistemas, perfis, pedidos, concessões, auditoria e a tabela de recados outbox_events. O comando npm run db:migrate aplica esse arquivo uma vez e anota o nome dele, para não criar as mesmas tabelas de novo.

    Abra db/migrations/001_init.sql. A tabela dos recados começa em outbox_events. O programa que lê o arquivo está em apps/api/src/db/migrate.ts.

  6. Encher o banco com gente fictícia

    O seed é a carga inicial de demonstração: Ana, Bruno, Clara, Diego, os sistemas ERP Fiscal e Folha, e um conflito de segregação entre lançamento fiscal e pagamento da folha. Pode rodar de novo sem duplicar as pessoas.

    Abra apps/api/src/db/seed.ts.

  7. Subir a API e a página

    npm run dev sobe dois processos ao mesmo tempo. A API escuta em 127.0.0.1:3000. A página Vite escuta em localhost:5173 e encaminha os caminhos /api e /health para a API. A página não fala com o MySQL. Quem fala com o banco é a API.

    Abra package.json na raiz, o script dev. A entrada da API é apps/api/src/main.ts. As rotas estão em apps/api/src/app.ts. A página está em apps/web/src/App.tsx. O encaminhamento está em apps/web/vite.config.ts.

  8. Login, sessão e papéis

    A senha é guardada com scrypt, não em texto puro. O login devolve um cookie que o JavaScript da página não consegue ler. Nas próximas chamadas a API lê esse cookie e descobre quem é a pessoa. Se o formulário mandar um campo role: admin, a API ignora. O papel vem da linha do usuário no banco.

    Abra apps/api/src/password.ts e apps/api/src/modules/identity/service.ts. O botão Entrar e o botão Sair estão em apps/web/src/App.tsx.

  9. Pedido, risco e decisão humana

    Ana escolhe um perfil e escreve uma justificativa. Na mesma ida ao banco, a API grava o pedido, calcula o risco e deixa o pedido em espera de aprovação, ou recusado se a regra for dura. Perfil privilegiado não se concede sozinho. Conflito com um acesso já ativo recusa. Bruno, gestor da Ana, aprova ou recusa. Recusa sem texto é rejeitada. Ana não consegue aprovar o próprio pedido.

    Abra apps/api/src/modules/access-guard/rules.ts para as regras. O fluxo do pedido está em apps/api/src/modules/access-requests/service.ts. Os estados permitidos estão em apps/api/src/modules/access-requests/transitions.ts.

  10. Deixar o recado na outbox

    Outbox, nesta aplicação, é a tabela outbox_events. Não é um programa. É uma fila dentro do próprio MySQL. Quando a API grava “aprovado”, ela grava também uma linha de evento, no mesmo commit. Se o commit falha, não fica aprovação sem recado, nem recado sem aprovação. Se a API desliga depois, o recado continua pending.

    Quem escreve o recado é a função recordSideEffects, no arquivo apps/api/src/modules/access-requests/service.ts. Ela insere em audit_events e em outbox_events.

  11. Criar o worker, o programa que escuta a fila

    O worker é um segundo programa Node. Ele não tem tela. Ele acorda, procura linhas pending e faz o trabalho que a API só anunciou. O comando é npm run dev:worker, noutro terminal. Ctrl+C encerra só ele. npm run dev não liga o worker, para o notebook não ficar com três processos o tempo todo.

    Abra apps/worker/src/main.ts. Esse arquivo só carrega apps/api/src/worker-main.ts. A lógica está em apps/api/src/modules/outbox/worker.ts. O conector simulado está em apps/api/src/modules/provisioning/connector.ts.

  12. Fazer o Sair voltar para o login

    O botão Sair já apagava a sessão no servidor. A página, porém, guardava na memória “ainda existe um usuário”. Por isso a tela não ia para o login. O ajuste joga fora essa memória quando o logout dá certo.

    O trecho está no onSuccess do logout, em apps/web/src/App.tsx.

O que é um evento, quem manda e quem escuta

Um evento é uma frase curta gravada no banco: “este pedido foi aprovado”. Não é um e-mail e não atravessa a internet. É uma linha com tipo, um identificador e um JSON pequeno, sem senha.

Quem manda

A API, dentro da mesma transação da mudança. O arquivo é apps/api/src/modules/access-requests/service.ts.

  • Criar pedido: access_request.submitted e access_request.risk_assessed.
  • Aprovar: access_request.approved.
  • Recusar: access_request.rejected.
  • Revogar uma concessão: access_grant.revoked.

Quem escuta

O worker. A função claim busca uma linha pending. A função dispatch escolhe o que fazer pelo texto do evento. As duas estão em apps/api/src/modules/outbox/worker.ts.

  • approved marca o pedido como em provisionamento e grava provisioning.requested.
  • provisioning.requested chama o conector.
  • Sucesso grava provisioning.completed e cria a concessão.
  • A frase recusa-simulada na justificativa grava provisioning.failed e o pedido fica failed, sem concessão.

O worker também escreve eventos novos. Ou seja: a API manda o primeiro recado, o worker escuta e, para continuar a corrente, manda o recado seguinte na mesma tabela. A lista completa dos nomes está em docs/events.md e de novo em packages/contracts/src/index.ts, na constante eventTypes.

Para ver um recado de verdade, no HeidiSQL abra o banco accessflow, tabela outbox_events. A coluna event_type é o nome. A coluna status diz se ainda está pending, se o worker pegou (processing), se terminou (processed) ou se desistiu (failed).

O que é o worker, sem jargão

Pense num balcão e num estoque. O balcão é a API: a pessoa pede, o balcão anota “aprovado” e coloca uma ficha numa caixa. A caixa é a tabela outbox. O estoque é o worker: de tempos em tempos alguém abre a caixa, lê uma ficha e vai até a prateleira colocar o acesso. A prateleira, aqui, são as tabelas access_grants, directory_accounts e directory_memberships. Não existe Active Directory.

Se o estoque estiver fechado, o balcão continua funcionando. O pedido fica approved e a ficha espera. Quando você roda npm run dev:worker, as fichas antigas são lidas. Ler a mesma ficha duas vezes não coloca dois acessos na prateleira: a concessão usa o pedido como chave única.

Se uma ficha dá erro técnico, ela volta para a caixa. A espera dobra a cada tentativa, até 15 minutos, no máximo 8 vezes. A recusa combinada do diretório fictício não fica nesse ciclo: ela encerra o pedido como falha.

Um clique, do começo ao fim

  1. Ana abre http://localhost:5173, entra e pede o perfil Consulta fiscal. Isso está em apps/web/src/App.tsx, função que chama POST /api/v1/access-requests.
  2. O Vite repassa a chamada para a API. Veja o proxy em apps/web/vite.config.ts.
  3. A rota em apps/api/src/app.ts chama createRequest.
  4. createRequest grava o pedido, roda assessRisk e insere os eventos. O pedido aparece para o Bruno como pending_approval, com uma nota.
  5. Bruno clica em Aprovar. A API grava approved e o evento access_request.approved.
  6. Se o worker estiver ligado, ele lê esse evento, pede o provisionamento e grava a concessão. O pedido passa a provisioned.
  7. Sair chama POST /api/v1/auth/logout, apaga a sessão e limpa a memória da página, que volta ao login.
